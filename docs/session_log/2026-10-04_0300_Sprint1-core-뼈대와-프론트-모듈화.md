- **대안**: 처음 명세는 `connect(path, role)` 을 공개했으나 dev 평가에서 에이전트 쪽 코드가 `role="reviewer"` 로 승인 전이를 직접 할 수 있는 D2 구멍으로 판명 → 공개 `connect` 를 agent 전용으로 변경.

## 트러블슈팅
### reviewer 1차 FAIL — 공개 agent 연결의 `INSERT OR REPLACE` 로 승인된 행이 덮어써짐 (Stage 1)
- **증상**: 승인된 행 `('d1', approved, human:h)` 가 `('d1', draft, agent:evil)` 로 바뀜. 수정 전에 직접 재현.
- **원인**: REPLACE 의 암묵적 삭제는 DELETE 권한 검사도 UPDATE 트리거도 거치지 않고, insert 트리거는 `NEW.state` 만 봤다. docstring 의 "트리거가 마지막 선" 문장도 사실이 아니었다.
- **해결**: insert 트리거에 id 충돌 `EXISTS`·위조 `decided_*`/`reason` 거부, 종결 행 DELETE 거부 트리거, `WITHOUT ROWID`, 트리거 3종 존재 검사. 수정 후 agent·우회 연결 모두에서 REPLACE·위조 INSERT·DELETE·UPDATE 거부를 직접 확인. docstring 정정.
- **커밋**: `230906e`
- **교훈**: 처음 테스트 178건으로는 못 잡았다. 통과 건수가 아니라 "이 테스트가 방어를 약화하면 실제로 빨개지는가"가 기준이다.

### reviewer 1차 FAIL — 테스트가 authorizer 에 의존하지 않는 가짜 성공 (Stage 2 T201)
- **증상**: 케이스의 `UPDATE drafts SET state='approved'` 는 authorizer 없이도 트리거가 막아서, `_agent_authorizer` 가 UPDATE 를 허용해도 테스트가 녹색이었다.
- **원인**: 단순 문장이 트리거 조건(`decided_by IS NULL`)에 걸림. 트리거 조건을 모두 만족하는 정상 형태 자기 승인 UPDATE 는 authorizer 없는 연결에서 **통과**한다(직접 재현).
- **해결**: 해당 문장 케이스 추가, 거부 메시지(`"not authorized"`) 고정, authorizer 없는 연결에서는 성공한다는 대조 테스트. 변형 실험(authorizer 를 메모리에서 약화)에서 8건 실패, 자기 승인 문장이 실제로 성공함을 직접 재현.
- **커밋**: `9553385`
