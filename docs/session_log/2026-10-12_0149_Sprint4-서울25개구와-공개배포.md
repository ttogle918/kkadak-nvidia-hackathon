## 결정과 맥락
### D30 — 채팅 "주변 행사"는 거리 기준, 공개 행사 검색 `excluded` 는 요약
- **계기**: T418 실서버 확인 중 두 가지가 드러났다.
  - 25개 구에서 채팅 주변 행사가 서울 전체 244건이 됐다(잠실 일정에 서초·종로 행사).
  - 행사 화면 검색 응답이 3.25MB(gzip 818KB)였다. 공개 송출 무료량(월 1GiB)을 금방 쓸 수 있다.
- **사람 결정**: "구로 나누기보다 거리로, 섞여도 됨", 요약은 "권장대로".
- **대안**:
  - 구로 거르기 — 경계 근처의 가까운 행사를 놓친다.
  - 문구만 "서울 전체"로 바꾸기 — 목록이 너무 길다.
  - 송출 상한만 두기 — 정상 사용자도 큰 응답을 받는다.
- **결과**: 3km·20건(T438). 검색 응답 3.25MB → 635KB(gzip 75KB)(T437).
### 배포 프로젝트를 전용으로 분리
- 기존 프로젝트에는 다른 서비스 5개(spendq·maintq)가 있어서 예산·무료 한도·비밀이 섞인다. 그래서 새 프로젝트를 만들었다(사람 선택).
- 결제 계정의 프로젝트 연결 한도(5개)에 걸렸다. 사람이 쓰지 않는 qmesh·calendar 의 결제만 해제했다(프로젝트는 남음).
- finallq(Cloud Run 서비스 3개)와 secureai-editor(Gemini API 사용)는 건드리지 않았다.
### 비밀은 `.env` 에서 파이프로 등록
- 처음에는 사람이 별도 터미널에서 직접 붙여 넣도록 안내했다. 키 값이 대화에 남지 않게 하려는 것이었다.
- 사람이 `.env` 를 쓰면 되지 않느냐고 물었다. 그래서 `core.llm.envfile` 로 읽은 값을 표준출력 파이프로 바로 `gcloud secrets` 에 넘겼다.
- 값은 화면·대화·로그 어디에도 나오지 않았고, 길이(70·96자)만 대조했다.
- 첫 시도는 `secrets create` 에 값이 안 들어가 빈 비밀이 생겼다. `versions add` 로 다시 넣었다.
### Netlify 는 Git 연결 없이 CLI 직접 배포
- 작업이 `sprint-3` 에 있고 아직 푸시하지 않았다. Git 을 연결하면 Netlify 는 보통 `main` 을 빌드한다.
- 빌드에 백엔드 주소가 필요한데, 그 주소는 Cloud Run 배포 뒤에야 나온다.
- 저장소 권한을 줄 필요도 없었다.
### TourAPI 는 배포에서도 켜 둠(사람 결정, 원인 확인 대기)
- Google Cloud 에서 `apis.data.go.kr` 로의 TCP 연결이 막혔다.
  - 진단 Cloud Run 작업으로 us-central1·asia-northeast3 를 모두 봤다. 첫 1회만 연결됐고, 그 뒤로는 키가 없어도 매번 실패했다.
  - DNS 는 풀리고, IP 를 직접 지정해도 연결되지 않았다.
  - 로컬은 0.16초에 정상이다.
- 사람은 "웹사이트 URL 을 안 넣어서일 수 있다 → 된다는 가정으로 켜 두기"로 정했다. 키를 덜 넣었는지, 운영계정이 필요한지도 물었다.
  - 키는 연결 뒤에 확인되므로 원인이 아니다.
  - SEOUL·TAVILY 키는 배포 런타임에서 쓰지 않는다.
  - 운영계정은 주로 트래픽 한도를 늘리는 것이라 원인이 아닐 가능성이 크다고 답했다.
- 남은 대안: 배포에서 끄기(`KC_TOURAPI_DAILY_CALLS=0`), 고정 출구 IP(VPC 커넥터 + Cloud NAT, 유료).
### hops(XFF): IP 제한 끔 유지
- 앱 접근 로그에는 Cloud Run 내부 주소만 남는다. 그래서 명세대로 로그 비교로 XFF 일치 위치를 확인할 수 없다.
- 비용은 세션·전역 제한과 일일 상한이 막는다(D24 ④).
### 메모리 2Gi 는 아직 그대로
- 실측은 로컬 컨테이너 최대 308MiB, 배포 p99 약 143MiB(LLM 포함)다. 1Gi 로 충분해 보인다.
- 낮출지는 사람이 정한다.
