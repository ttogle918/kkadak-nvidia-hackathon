# 서울 API 행 수 · 자원(RSS) 기준선 — 1차 (T408, 2026-10-10)

제품 코드 변경 없음. 스크립트: `scripts/measure_seoul_rows.py`(서울 API 1행 요청 1회), `scripts/measure_runtime.py`(로컬 프로세스만).
실호출: 서울 API **1회**, NVIDIA **0회**. 키 값·원응답은 어디에도 남기지 않았다. `var/` 는 읽기만 했고 측정용 상태(캐시·hitl·audit)는 임시 폴더에 만들었다.
조건: WSL2, 카탈로그 `var/catalog`(entries 8,719건 · 4개 구), 색인 `var/index/kcontext.db`. 이 값은 **1차**다 — 2차(T418, 25개 구 카탈로그·새 색인)는 같은 스크립트로 아래 "2차" 칸에 채운다.
RSS 는 `/proc/PID/status` 의 VmHWM(자식, 10ms 표본) 또는 VmRSS(합계, 20ms 표본) 이고 단위는 MiB 다. wait4 의 `ru_maxrss` 는 자식이 부모(측정 스크립트, 약 34MiB)의 RSS 를 바닥으로 물려받아 작은 자식에서 부정확해 참고값으로만 남겼다(검색 자식처럼 큰 자식에서는 VmHWM 과 같다: 199.3).

## 1. 서울 API 총건수 (실측)

| 항목 | 값 |
|---|---:|
| `culturalEventInfo` `list_total_count` | **19,586** |
| 현재 코드의 쪽 상한 (`max_pages=30` × 1000) | 30,000 |
| 25개 구로 넓혀도 잘리는가 | **아니오** (19,586 < 30,000, 여유 10,414건 = 약 53%) |

- 서울 API 는 구 필터 없이 서울 전체를 한 번에 준다. 현재 4개 구 카탈로그도 같은 19,586행을 받아 `in_target=no` 인 행을 버린 결과다. 25개 구는 거의 전부가 남는다 — 쪽 상한은 4개 구든 25개 구든 같은 값(19,586)에 걸린다. 지금도 잘리지 않았다는 뜻이다.
- 카탈로그 4개 구 관찰값은 8,712건(서울 API) = 총건수의 **44.5%**: 종로구 4,918 · 중구 1,911 · 마포구 1,167 · 강남구 595 · 구 미상(`unknown`, 남겨둔 행) 121. entries 8,719건 = 이 8,712 + 사이트 출처 7.
- 주의(추정 아님, 구조): 서울 API 는 2021년 것부터 쌓인 이력까지 준다(오래된 행사 `obs_id` 가 있다). 그래서 총건수는 시간이 지날수록 커진다. 증가 속도는 이번 1회 호출로는 알 수 없다 — 30,000 에 닿기까지의 여유만 알 수 있다. T418 이 총건수를 다시 읽어 `truncated` 를 확인하고, T416 이 쪽 상한을 인자로 둘 때(`--max-pages` 기본 60 = 6만) 여유가 생긴다.
- 전체 쪽 수집 통계(구별 수, 끝나지 않은 행 수, 좌표 있는 행)는 `measure_seoul_rows.py --full` 이 낸다. **호출 상한(3회) 때문에 이번에는 돌리지 않았다** — T418(또는 호출 여유가 있을 때)에서 채운다. 대신 현재 카탈로그 관찰값(로컬 파일)에서: 끝나지 않은(`end_date >= 2026-10-10`) 서울 API 행 159건(1.8%).

## 3. 25개 구 추정 (**추정** — 측정값 아님)

가정: 25개 구 entries ≈ 서울 API 총건수 19,586 + 사이트 출처 7 ≈ 19,600건. 배수 f = 19,586 / 8,712 = **2.25**(4개 구 대비). 같은 날 같은 API 에서 4개 구 카탈로그를 만들었다는 가정이고, 구별 건수는 이번에 직접 못 쟀다(§1). 모든 항목을 건수에 선형으로 놓았다. 병합·중복 제거(T416 의 월 버킷 병합)나 T433 의 개선은 반영하지 않았다.

| 항목 | 4개 구 (실측) | 25개 구 (추정) | 근거 |
|---|---:|---:|---|
| entries 건수 | 8,719 | 약 19,600 | 총건수 + 사이트 출처 |
| entries.json | 22.2MiB | **약 50MiB** | ×2.25 |
| observations.json | 20.7MiB | 약 47MiB | ×2.25 |
| 검색 자식 최대 RSS | 199.3 | **약 413** | 고정 28 + (199.3 − 28) × 2.25 |
| 검색 시간(자식 1회) | 약 7.1초 | **약 16초** | 선형(모델 변환이 87%) |
| 끝나지 않은 행 | 159 | 약 360 | ×2.25 (끝난 행이 대부분) |
| 실록 색인 `kcontext.db` | 42.9MiB (키워드 기사 4,822건) | 4개 구 그대로 (D28 기본) | 키워드를 고른 구만 늘어난다. 25개 구 전부에 키워드가 있다면 기사 수에 비례해 최대 약 270MiB 까지 갈 수 있는 거친 상한(구 수 비례 25/4, 기사 중복은 반영 안 함). 파이프라인 RSS 는 색인을 읽어 쓰는 방식이라 33.8 에서 크게 변하지 않을 것으로 본다(확인은 2차) |

- 검색 시간 16초는 자식 기본 시간 제한(60초)에는 들지만 채팅 시간 예산·사용자 체감으로는 길다 — **T433(변환 건수 줄이기) 없이 25개 구로 가면 목표 1.5초와 10배 이상 차이가 난다.** T433 이후 RSS 도 같이 줄 수 있어 2차 측정이 필요하다.

## 4. D27 Cloud Run 메모리 설정 제안 (**추정 기반**, 2차에서 확정)

공식: `--memory ≥ 최대 RSS × 1.5 + /tmp 사용량`(T402 §3: 쓰기 가능한 파일시스템이 메모리에 합산된다).

- 25개 구, D24 동시성(검색 자식 2개 + backend) 추정 최대: backend 72 + 413 × 2 = **약 900MiB** (추정 · 파이프라인 1 + 검색 1 동시이면 72 + 413 + 34 ≈ 520 이라 더 작다)
- × 1.5 = 약 1,350MiB
- `/tmp`: 현재 hitl.db·audit·캐시는 합쳐 0.2MiB 안팎. 공개 모드에서 늘어나는 것(자식 임시 bundle ≤1MiB × 동시 2, audit·세션 파일)을 **여유 64MiB 로 가정**(가정값 — 실측 아님, 공개 모드 audit 크기는 T426 에서 확인).
- 합계 약 1,414MiB → **권고 `--memory 2Gi`, `--cpu 1`**.
  - 검색 자식 동시성을 1로 제한하면(백엔드 72 + 413 = 485 × 1.5 + 64 ≈ 790MiB) 1Gi 도 가능하다.
  - 4개 구 그대로(실측 최대 430.8 × 1.5 + 64 ≈ 710MiB)면 1Gi 로 충분하다.
  - T433 이후 자식 RSS 가 줄면 재계산한다.
- 이 숫자는 **추정**이다. 확정은 2차(T418: 25개 구 카탈로그 + T433 적용 후 같은 스크립트로 재측정)의 최대 RSS 로 하고, 페이지 캐시·mmap 이 컨테이너 한도에 합산되는지(T402 §3 미확인)는 T426 에서 본다.
