# 행사 검색 프로파일 (T407, 2026-10-10)

동작 변경 없음. `uv run python scripts/profile_catalog_search.py --catalog var/catalog --trip 2026-10-15..2026-10-15 --trip 2026-10-15..2026-10-18 --runs 3`
(`var/catalog` 읽기만, 실호출 없음). 구간은 `CatalogStore.load_entries` + `api._search` 순서를 스크립트 안에서 재현한 값(재현 경로)이다.
일정(itinerary) 없는 요청이라 `fit_event` 구간은 포함하지 않는다. 숫자는 3회 중앙값(ms). 다른 태스크가 병렬로 돌고 있어
실행 간 편차가 ±15% 정도 있다(아래는 두 번째 실행, 첫 실행도 같은 결론).

`excluded` 생성은 검색 판정 구간(약 190ms)에 들어 있고, 그 안에서 `excluded` 에 해당하는 몫은 더 작다.

## 결론

- **`excluded` 직렬화·전송은 병목이 아니다.** `excluded` 1.1MB 직렬화는 약 8ms, 응답 전체 직렬화도 약 10ms(전체의 0.1%)이고,
  부모의 파싱도 약 5ms 다. 판단 규칙(`result_dumps` + 전송 ≥ 50%)에 한참 못 미친다(약 0.3%).
  `excluded` 생성까지 포함한 검색 판정도 전체의 2.5% 다.
- **병목은 `entry_from_dict` 8,719회(약 6.5~7.3초, 전체의 약 87~93%)다.** 원인은 JSON 파싱(약 0.1초)이 아니라 건당 약 0.75~0.8ms 인 모델 변환
  (`_load` 형식 검증 + `_check_entry`)이다. 부차적으로 `entries.json` 을 `entries_built_at()` 에서 한 번 더 파싱하는 비용이 약 0.1~0.3초 있다.
- **D29 는 필요 없다(올리지 않는다).** `excluded` 를 요약으로 바꿔도 시간이 거의 줄지 않는다(약 10ms).
- 목표(≤1.5초)는 A안(`excluded` 보존)으로도 도달 가능하다. 다만 T433 의 "검색 전 사전 제외 색인"만으로는 부족할 수 있다. 모델 변환이 검색 판정보다
  앞에 있어서, 사전 제외 색인이 **변환할 건수 자체를 줄이는** 구조(통과한 후보만 `entry_from_dict`, 또는 `excluded` 용으로는 id·title·reason 에 필요한
  최소 필드만 읽기)여야 효과가 있다. 25개 구로 늘면 entries 가 더 늘어 이 구간이 비례해 커진다(건수 선형).
- 단계별 후보(참고, 코드는 바꾸지 않았다): 검증을 건너뛰는 신뢰 경로, 변환 결과 캐시, 후보 선별 후 변환.
