01 · Problem

우리는 ‘관광지 부족’이 아니라 ‘발견의 실패’를 해결한다

①

정보가 늦게 확정된다

지역 축제·야장·상권 이벤트는 여행자가 항공권·숙박을 예약한 뒤 공개되는 경우가 있어 사전 여행계획에 반영되기 어렵다.

②

공식 정보가 흩어져 있다

관광공사, 시청·구청, 문화기관, 상권·시장 페이지 등 출처가 분산되어 있어 여행자가 직접 모두 찾아야 한다.

③

검색은 맥락을 연결하지 못한다

“무슨 행사가 있다”는 사실보다, 내 일정에 넣을 수 있는지·왜 의미가 있는지·정보가 최신인지 판단하는 과정이 더 어렵다.

05 · Data Strategy

야장·축제 데이터는 ‘공식 API 우선 + 지자체 웹 보완’이 최적

시청·구청 홈페이지 검색은 필요하지만 1차 데이터원으로만 의존하면 포맷·갱신주기·페이지 구조 변경 리스크가 크다.

우선순위데이터원활용추천 이유주의점
1순위한국관광공사 TourAPI전국 관광지·위치기반·행사/축제·숙박구조화된 전국 단위 공공 API. searchFestival2, locationBasedList2 제공모든 소규모 상권 이벤트가 들어오는 것은 아님
1순위서울 열린데이터광장 / 실시간 도시데이터서울 문화행사 + 혼잡·교통·날씨 결합서울 주요 장소의 문화행사와 실시간 도시상황을 한 흐름으로 결합 가능장소·API별 범위 확인 필요
1순위문화포털 OpenAPI공연·전시·문화행사 보강문화·예술 정보 확장에 적합지역축제/상권 이벤트는 별도 보완 필요
2순위시청·구청·관광재단 공식 홈페이지야장, 골목행사, 상권 이벤트, 공지사항API에서 누락되는 ‘로컬한 최신 이벤트’ 발견 가능HTML 구조 변동, 중복·종료 공고 존재
2순위공식 보도자료·공지 RSS/피드 (제공 기관에 한함)일정 변경·취소·추가 공지크롤링보다 변경 감지에 유리모든 기관이 RSS를 제공하는 것은 아님
3순위공식 SNS/행사 운영주체 채널당일 변경, 현장 운영시간 보완늦게 바뀌는 행사 운영정보 포착발견용으로 사용하고 핵심 사실은 공식 원문과 교차검증
보조지도/경로 API거리·소요시간·대중교통/도보 계산추천을 실제 일정에 넣을 수 있게 만드는 핵심 계산사업자별 API 이용조건·쿼터 확인

추천 수집 파이프라인

① API batch 수집 ↓ ② 공식 웹 신규 공고 탐색 ↓ ③ 이벤트 정규화 - title / date / time / lat,lng / source ↓ ④ 중복 병합 ↓ ⑤ 최신성·신뢰도 점수화 ↓ ⑥ Agent 검색용 Vector/Structured DB 저장 ↓ ⑦ 변경 감지 → 사용자 일정 재평가

신뢰도 점수 예시

공식 지자체/공공기관 원문 +40 공식 행사 주최기관 원문 +30 2개 이상의 독립 공식 출처 +15 최근 7일 이내 갱신 +10 날짜·장소·시간 완전 일치 +5 -------------------------------- 취소/변경 상충 정보 → 보류 SNS 단독 출처 → '확인 필요'

점수 자체는 기획용 예시이며 실제 배점은 테스트 후 조정.

User Web일정·날짜·관심사 입력

Official Data LayerTourAPI · 서울 API · 문화포털 · 지자체 공식 페이지

WHY AGENT

검색 결과를 나열하는 것이 아니라, ‘나에게 지금 쓸 수 있는가’를 판단합니다.

AI Agent는 자유형 일정 이해, 정보 충돌 판단, 개인화 우선순위, 역사·문화 맥락 설명을 담당합니다. 거리·시간은 지도 엔진, 권한은 OpenShell이 담당합니다.

06 / 08
DATA & TRUST

공식 API를 기본으로, 지자체 공식 웹을 보완 수집합니다.

TourAPI 행사·위치정보 + 서울 실시간 도시데이터 + 문화포털 + 시청·구청 신규 공고. 출처·업데이트 날짜·충돌 여부를 기준으로 신뢰도를 붙입니다.

07 / 08
OPENSHELL

Agent가 잘못 판단해도 secret 파일과 비허용 네트워크에는 접근할 수 없습니다.

관광데이터 read-only, 결과 캐시 write 허용, restricted/secret 차단, 승인 도메인만 allowlist. 심사위원이 공격 프롬프트를 입력해도 실행 경계가 유지되는 장면을 보여줍니다.
