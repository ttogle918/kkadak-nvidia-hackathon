2. 에이전트 한 번의 실행 흐름

사용자 메시지 한 건이 카드가 되고 사람 승인과 감사 기록에 이르기까지. 태그: 코드 결정적 처리, LLM 모델 판단(설계), 차단, 사람 승인, 계획 Sprint 2 문서상 아직 구현 전, 구현됨 확인 시점 트리에 코드 있음.

  1. 사전: 자료 수집 · 색인 (대화 밖)

    호스트 수집기가 실록 XML·행사 자료를 모아 var/ 아래 로컬 색인·JSONL 로 만든다. 대화 중에는 외부 출처를 긁지 않는다. 출처마다 이름·위치·URL·원문 구절·수집일·등급을 함께 저장한다.

    코드색인 저장소실록·행사 수집기

  2. 입력 접수 · 상황 이해

    프론트 → POST /api/messages. backend 가 길이(빈 문자열·2000자 초과 422)와 동시 실행(429)을 확인하고 파이프라인을 별도 프로세스로 띄운다.

    • 설계(04): 경량 모델이 일정·빈 시간·의도를 추출, 불분명하면 한 번만 되묻는다.
    • Sprint 2: 채팅에서 일정을 추출하지 않고 데모 상황 파일을 쓰며 답에 그렇게 밝힌다.
    • 설계(04 §3.6): 사용자 입력에도 안전 검사.
    코드설계: 경량 LLM계획

  3. 후보 수집

    지역(중구·종로구·마포구·강남구)과 날짜 같은 구조화 조건을 먼저 걸고, 그다음 로컬 색인(FTS5 trigram)에서 이야기·행사 후보를 찾는다. 날짜가 여행 기간과 맞지 않는 행사는 여기서 코드가 뺀다. 탈락 후보는 이유(관련 없음 · 중복 · 신뢰 불가 · 기간 지남)와 함께 기록한다.

    코드계획

  4. 이야기·행사 판정 (주입 차단)

    • 먼저 주입 차단: 자료 제목·본문을 core.guard.scan 으로 검사. 주입 판정이면 레코드를 제외하고 "지시문 포함"으로 탈락 기록, 의심이면 남기되 "자료에 지시문 의심 문구" 주의를 붙인다. 자료 속 지시문은 따르지 않고 기록한다.
    • 출처 등급(S~D)과 날짜는 코드가 붙여서 판정에 넘긴다. 모델이 등급을 정하지 않는다.
    • 같은 대상인지 확인 → 질문 유형에 맞는 출처 → 날짜(운영 정보는 최신 공식, 역사 사실은 최신이 이기지 않음) → 독립 출처 수 → 해결 안 되면 이설·보류.
    • 딱지: 이야기 = 기록/전승/추정, 행사 = 확인됨/확인 필요/보류. 취소된 행사는 제외. 근거가 없으면 unverified 로 카드를 만들지 않는다.
    주입 차단Sprint 2: 규칙 기반설계: 대형 LLM계획

  5. 경로 (이야기 길)

    도보 거리·시간은 경로 엔진 값만 쓴다(모델 추정 금지). 가장 빠른 경로 → 주제별 경유지 → 우회 한도 초과 경로는 코드가 버림 → A·B·C 로 중립적으로 놓고 배지(가장 빠름·이야기 가장 많음·추천)를 붙인다. 구간 이름은 해당 카드의 제목·본문에서만 가져온다.

    • 공급자 우선순위(D9): ① PlayMCP 카카오맵 MCP ② OSM 도보 엔진 ③ 직선거리 추정. ③은 estimated: true, 화면에 "예상 시간".
    코드·경로 엔진경유지 묶기: 설계 LLM계획

  6. 일정 맞추기 · 카드 만들기

    행사 운영 시간과 빈 시간의 겹침, 들렀다 가는 추가 이동(동선), 다음 일정·막차 영향을 코드가 판정한다. 동행 조건(미성년이면 술 중심 장소 제외, 비 오면 야외 제외)도 코드. 남은 것 중 1~3건을 카드로 만든다. 본문 문장마다 근거 출처 번호를 달고, 번호 없는 문장은 내보내지 않는다. 사용자가 정한 일정은 바꾸지 않는다.

    코드우선순위·문장: 설계 LLM계획

  7. 검증 · 산출물 쓰기 (제안 지위)

    모든 카드·경로·판정을 계약 검증기로 확인한 뒤 var/output/<run_id>/ 에 kc-bundle/v1 을 쓰고 current.json 을 원자적으로 교체한다. 검증 실패면 묶음을 쓰지 않는다. 이 산출물은 draft 와 같은 "제안"이며 상태 전이를 담지 않는다. 설계(04 §3.6): 최종 출력에도 안전 검사.

    코드계약 검증기묶음 쓰기

  8. 사람 승인 (HITL)

    화면이 backend 에서 카드·근거를 읽어 보여준다. 에이전트가 허용 목록 밖 출처를 원하면 kc_request_source 로 hitl draft 만 만든다. 승인·반려는 backend 의 review 라우터에서 사람이 한다.

    • 요청 본문에 신원 필드가 없고 서버가 주입한다. 본인 승인은 403 self_approval, 이미 결정된 항목은 409.
    • 결정 대상은 draft: 항목뿐. audit: 항목은 읽기 전용.
    • "일정에 추가"(user_state)는 이번 스프린트에서 화면 상태일 뿐 서버 상태 전이가 아니다.
    • 사람이 승인해도 policy.yaml 은 사람만 고친다. 에이전트·dev 는 수정하지 않는다(D7).
    사람 승인승인 API · hitlMCP 도구(선택)

  9. 감사 로그

    단계마다 도구 호출을 audit/v1 JSONL 한 줄로 기록한다(호출 직전 이벤트 발행). 주입 차단은 오류로 기록한다. backend 의 GET /api/audit 이 이를 보안 로그로 보여주고(ok·deny·pend·approved·rejected), policy_proposer 는 이 기록만 입력으로 받아 정책 초안을 만든 뒤 사람 승인을 기다린다. 화면에서 앱 수준 차단은 "(앱 차단)"으로 OpenShell 차단과 구분한다.

    코드audit · policy_proposer

3. 신뢰 경계 · 차단 / 승인 지점

"누가 무엇을 못 하게 하는가"를 경계별로 정리했다. 좌측 색: 빨강 = 자동 차단, 주황 = 사람 승인, 초록 = 데이터 취급 규칙.

샌드박스 → 외부 네트워크

정책 밖 접속은 거부(기본 전부 차단). 허용 항목은 이유와 ALLOWED/DENIED 실측을 주석에 남긴다. 새 출처가 필요하면 draft 로 요청하고 사람이 승인한다.

프로세스 경계

MCP 서버와 backend 는 서로 import 하지 않는다. backend 는 domains 도 import 하지 않고 파이프라인을 subprocess 로 실행해 파일만 읽는다. APP_PROCESS_ROLE=agent 프로세스에서는 backend 가 기동을 거부한다.

D3 · D10 · sprint-2 게이트

LLM 이 하지 않는 일

거리·시간, 날짜 겹침, 우회 한도, 다음 일정 충돌, 출처 등급 부여는 코드와 엔진이 한다. 등급·날짜는 코드가 붙여 모델에 준다.

03 §3 · 08 §1 · 설계

확인 필요

문서끼리 어긋나거나 문서에 비어 있는 칸이다. 이 흐름도는 이 항목들을 임의로 해소하지 않았다.

  1. 추론 경로가 서로 다르다. CLAUDE.md·D1 은 샌드박스 안 추론을 inference.local 로만 한다고 하는데, AGENT_CONTEXT 5.1 은 OpenShell v0.1.x 에서 inference.local 이 제거돼 프로바이더 네이티브 엔드포인트를 직접 호출한다고 적었다. 로컬 실측은 openshell 0.0.116 이다. 어느 방식이 맞는지 설치 버전 문서로 확인해야 한다.
  2. 대상 지역 서술 정리 상태. 개발 문서(00~09)는 4개 구 위주로 이미 수정됐고, regions/*.json 은 중구·종로구·마포구·강남구다. AGENT_CONTEXT 3.2 는 중구·종로구·마포구·강남구를 2026-10-07 에 확정했다고 적었고, 지역 정의는 regions/*.json 과 일치한다. 지역 파일의 bbox·center 는 null 이라 아직 채워지지 않았고(H7), 구 경계와 실록 지명 매핑도 검증 전이다.
  3. backend·오케스트레이터 위치. 03 §1 은 "한 샌드박스 안의 한 프로세스가 아니다"라고 쓰고, 샌드박스 배치는 §6 에서 미정으로 둔다(어느 프로세스를 샌드박스 안에 넣을지 정하지 않았다). CLAUDE.md·D10 은 backend 를 사람 전용 승인 API 로, 파이프라인은 별도 프로세스(APP_PROCESS_ROLE=agent)로 분리한다. 파이프라인이 실제로 샌드박스 안에서 도는지, backend 가 어디서 도는지는 문서에 없다(샌드박스 이미지는 Sprint 2 범위 밖).
  4. NemoClaw/OpenClaw 와 MCP 연결. 04 는 "한 오케스트레이터가 단계를 호출"하는 구조이고 NemoClaw 는 선택이다. D10 은 에이전트 런타임 연결을 이번 범위 밖으로 뒀고, 구성도의 런타임 칸은 CLAUDE.md 배치를 따른 것이다. 도구 이름도 04(geocode·walk_route·search_stories…)와 sprint-2 T217(kc_search_sources·kc_plan_walk·kc_request_source)이 다르다.
  5. LLM 이 하는 일의 범위. 04 는 일정 이해(경량 모델)·판정·경로 구성·작성(대형 모델)·안전 검사(Safety Guard NIM)·포스터 읽기(비전)를 쓴다. Sprint 2 는 규칙 기반 판정만 만들고 LLM transport(T223)는 이월, 채팅 일정 추출과 구청 게시판·포스터 읽기는 하지 않는다. 안전 검사도 실제로는 규칙 기반 core.guard 다. 흐름도의 LLM 표시는 "설계" 기준이다.
  6. 로컬 NIM · GPU. 03·AGENT_CONTEXT 는 L40S 로컬 NIM(host.openshell.internal)을 쓴다. D6 은 local 백엔드를 호스트 경로 전용으로 하고, 이 PC 에는 GPU 가 없으며 로컬 엔드포인트 값은 미확인 가정이다. 구성도에는 로컬 NIM 을 그리지 않았다.
  7. 데이터 저장 방식. 03 은 지식 DB·사용자 DB(SQLite 2개, 사용자 DB 는 세션 종료 시 삭제)를 말하고, 02 는 카드 상태를 사용자 DB 에 저장한다. Sprint 2·D8·D10 은 FTS5 로컬 색인 + var/ 파일 묶음이며 user_state 는 화면 상태뿐이다. 사용자 DB 가 언제 생기는지 문서에 없다.
  8. "승인"의 두 가지 뜻. 02 §6·AGENT_CONTEXT 는 OpenShell 정책 어드바이저(openshell rule approve) 승인을 시연한다. Sprint 2 는 샌드박스 없이 hitl draft 승인(앱 수준)까지만 한다. 둘을 어떻게 연결하는지(draft 승인 → 정책 반영) 문서에 없고, OpenShell 로그 형식도 미확인이라 어댑터만 두기로 했다(D4).
  9. 수집이 어디서 도는가. 03 은 수집 작업을 샌드박스(ingest)로 분리하는 확장안을 제시하지만 D7 은 호스트 오프라인 수집기로 정했다. 호스트 수집기 키 변수명(DATA_GO_KR_SERVICE_KEY·SEOUL_OPENAPI_KEY)은 "제안"이다.
  10. 도보 경로 공급자와 카카오 호출 위치. 04 는 "경로 엔진 값만"이라 하고 D9 는 추정값을 "예상"으로 허용한다. PlayMCP 카카오맵의 서버 호출 가능 여부는 미확인(H5)이고, policy.yaml 의 kakaomap_mcp 항목은 미실측이며 호스트 쪽인지 샌드박스 쪽인지 의도가 정리되지 않았다(사람 선행 #3).
  11. 구현 진행 상태. 확인 시점 트리에는 contract·index·regions·core(llm·hitl·guard·audit·policy_proposer)·backend 승인 API 가 있다. judge·geo·pipeline·ingest·MCP 도구는 아직 없고 sprint-2 완료 기록은 Stage 1 까지다. 00~09 번 문서는 아직 git 에 추적되지 않는다(untracked). 이 흐름도의 Stage 2 이후 단계는 계획 기준이다.
